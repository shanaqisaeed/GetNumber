# 3. تفکیک معماری Normal Node و Central Node

این قسمت مهم‌ترین اصل معماری پروژه است.

ما دو محصول مستقل خواهیم داشت.

## 3.1. Normal Node

مخزن فعلی GetNumber:

https://github.com/shanaqisaeed/GetNumber

این پروژه فقط یک Normal Node است.

تمام توسعه‌های فعلی باید روی همین پروژه و با حفظ قابلیت‌های موجود انجام شوند.

مسئولیت‌های Normal Node:

- مدیریت کاربران
- دریافت و مدیریت شماره‌ها
- ارسال و دریافت پیام
- مدیریت APIهای اختصاصی
- کیف پول کاربران
- خرید و تخصیص شماره
- ارتباط با Central Node
- اجرای فرمان‌های دریافتی از Central
- مدیریت پیش‌شماره‌های اختصاص‌یافته
- مسیریابی پیام‌های بین نودی
- گزارش وضعیت و سلامت نود

**ممنوعیت مهم:**

قابلیت‌های مدیریتی اختصاصی Central Node نباید به هسته اجرایی Normal Node اضافه شوند.

Normal Node نباید مسئول صدور Global Node ID برای دیگران، مدیریت مالکیت جهانی پیش‌شماره‌ها یا مدیریت شبکه مرکزی باشد.

## 3.2. Central Node

Central Node یک پروژه مستقل خواهد بود که روی زیرساخت سرورهای خودمان اجرا می‌شود.

در صورت نیاز، سورس فعلی می‌تواند به فولدر دیگری کپی شود، اما نباید صرفاً یک نسخه کامل از GetNumber باشد که قابلیت‌های Central به آن اضافه شده‌اند.

Central Node باید هسته مستقل داشته باشد.

مسئولیت‌های آن:

- ثبت خودکار نودها
- مدیریت هویت جهانی نودها
- صدور و مدیریت API Key
- مدیریت مالکیت پیش‌شماره‌ها
- مدیریت پوشش شبکه
- مدیریت فرمان‌های نودها
- مسیریابی ارتباطات
- مدیریت سیاست‌های امنیتی
- ثبت گزارش ارتباطات
- مدیریت وضعیت نودها
- مدیریت محدودیت‌ها و Rate Limit

دو پروژه باید از طریق یک پروتکل استاندارد و مستقل از زبان برنامه‌نویسی با یکدیگر ارتباط برقرار کنند.

قرارداد API باید به شکلی طراحی شود که توسعه‌دهنده بتواند Normal Node را با زبان برنامه‌نویسی دیگری نیز پیاده‌سازی کند.

## Phase 4: معماری کیف پول و Coin

یک سیستم Wallet مستقل و قابل توسعه پیاده‌سازی شود.

### 4.1. واحد اعتبار

واحد داخلی سیستم:

`COIN`

نرخ اولیه:

`1 TRX = 1 COIN`

این نرخ باید از تنظیمات سیستم قابل تغییر باشد.

قیمت اولیه هر شماره:

`1 COIN`

قیمت شماره نیز باید قابلیت تغییر از پنل مدیریت داشته باشد.

مبالغ مالی نباید با Float پردازش شوند. از Decimal با دقت مناسب استفاده کن.

### 4.2. معماری مالی

سیستم باید دارای دفترکل تراکنش‌ها (Ledger) باشد.

هر تغییر موجودی باید دارای رکورد مستقل باشد.

انواع تراکنش:

- DEPOSIT
- NUMBER_PURCHASE
- ADMIN_CREDIT
- ADMIN_DEBIT
- REFUND
- REVERSAL

قواعد:

1. تراکنش‌های مالی نباید حذف یا به‌صورت مخرب ویرایش شوند.
2. اصلاح اشتباه مالی با تراکنش معکوس انجام شود.
3. هر تراکنش شناسه یکتا داشته باشد.
4. جلوگیری از ثبت دوباره تراکنش الزامی است.
5. تمام تغییرات موجودی باید Atomic باشند.
6. برای جلوگیری از Race Condition از Database Transaction و Lock مناسب استفاده شود.
7. موجودی کیف پول باید از Ledger قابل تطبیق باشد.

### 4.3. خرید شماره

فرآیند خرید شماره:

1. کاربر درخواست شماره می‌دهد.
2. موجودی کیف پول بررسی می‌شود.
3. اگر موجودی کافی بود، اعتبار لازم کسر می‌شود.
4. شماره به کاربر اختصاص پیدا می‌کند.
5. نتیجه خرید ثبت می‌شود.

اگر موجودی کافی نبود:

- درخواست خرید متوقف شود.
- کاربر به صفحه کیف پول هدایت شود.
- مبلغ موردنیاز برای خرید مشخص باشد.

اگر تخصیص شماره شکست خورد، مبلغ باید با مکانیزم Refund به کاربر بازگردد.

تمام مراحل باید در برابر درخواست‌های هم‌زمان امن باشند.

### 4.4. داشبورد کاربر

در داشبورد، موجودی Coin نمایش داده شود.

با کلیک روی شارژ کیف پول، کاربر به بخش مربوط در پروفایل هدایت شود.

صفحه تراکنش‌ها نیز ایجاد شود.

قابلیت‌ها:

- مشاهده موجودی
- مشاهده گردش حساب
- مشاهده تراکنش‌ها
- فیلتر تراکنش‌ها
- مشاهده وضعیت شارژ
- مشاهده جزئیات هر تراکنش

### 4.5. پنل مدیریت مالی

ادمین باید بتواند:

- موجودی کاربران را مشاهده کند.
- حساب کاربر را شارژ کند.
- از حساب کاربر اعتبار کسر کند.
- تراکنش دستی ثبت کند.
- دلیل تغییر موجودی را ثبت کند.
- تراکنش‌ها را جستجو و فیلتر کند.
- گزارش مالی دریافت کند.
- تراکنش‌های ناموفق و مشکوک را بررسی کند.

تمام عملیات مدیریتی باید Audit Log داشته باشند.

## Phase 5: سیستم پرداخت و اتصال صرافی‌ها

### 5.1. معماری Payment Gateway

پرداخت نباید مستقیماً به یک صرافی وابسته باشد.

یک Interface مستقل طراحی شود.

پیشنهاد:

`PaymentGatewayInterface`

هر صرافی باید Adapter اختصاصی خودش را داشته باشد.

برای مثال:

- NobitexGateway
- TronWalletGateway
- FutureExchangeGateway

نام‌ها نمونه هستند و ساختار نهایی باید با معماری واقعی پروژه هماهنگ شود.

هر Gateway باید بتواند:

- ایجاد درخواست پرداخت
- دریافت اطلاعات کیف پول
- دریافت اطلاعات تراکنش
- بررسی TX Hash
- اعتبارسنجی مبلغ
- اعتبارسنجی شبکه
- اعتبارسنجی مقصد
- بررسی تأییدیه‌های تراکنش
- مدیریت وضعیت پرداخت

را انجام دهد.

خرابی یک Gateway نباید باعث اختلال در سایر Gatewayها شود.

### 5.2. اتصال نوبیتکس

مستندات ارائه‌شده:

https://apidocs.nobitex.ir/api_key/%DA%A9%D9%84%DB%8C%D8%AF-api

مستندات رسمی مرتبط با API Key، کیف پول‌ها، آدرس واریز و اطلاعات تراکنش‌ها را بررسی کن.

فرض نکن API Key به‌تنهایی امکان تمام عملیات پرداخت را فراهم می‌کند.

ابتدا محدودیت‌ها و Endpointهای واقعی مستندات را بررسی کن.

فرآیند پرداخت:

1. کاربر درخواست شارژ ثبت می‌کند.
2. سیستم از Gateway مربوطه درخواست ایجاد آدرس پرداخت می‌کند.
3. صرافی کیف پول یا آدرس اختصاصی ارائه می‌دهد.
4. آدرس به کاربر نمایش داده می‌شود.
5. کاربر TRX را انتقال می‌دهد.
6. TX Hash را در سیستم وارد می‌کند.
7. سیستم تراکنش را استعلام می‌کند.
8. صحت مبلغ، شبکه، مقصد و وضعیت تراکنش بررسی می‌شود.
9. در صورت تأیید، موجودی Coin افزایش پیدا می‌کند.

### 5.3. تأیید دستی و خودکار

هر دو روش باید وجود داشته باشند.

**تأیید خودکار:**

Cron Job تراکنش‌های منتظر را بررسی کند.

**تأیید دستی:**

ادمین بتواند TX Hash را وارد کند یا تراکنش ثبت‌شده را مجدداً استعلام بگیرد.

بررسی دستی نباید به معنی دور زدن اعتبارسنجی بلاکچین باشد.

### 5.4. Cron Job

سیستم باید تراکنش‌های Pending را به‌صورت دوره‌ای بررسی کند.

فاصله بررسی اولیه:

هر یک دقیقه.

قواعد مهم:

- هر TX Hash فقط یک بار قابل استفاده باشد.
- هر پرداخت فقط یک بار اعتبار ایجاد کند.
- تراکنش تأییدنشده اعتبار ایجاد نکند.
- درخواست‌های تکراری باعث شارژ دوباره نشوند.
- وضعیت‌های پرداخت به‌درستی مدیریت شوند.
- خطاهای Gateway ثبت شوند.
- Retry با Backoff انجام شود.

### 5.5. پشتیبانی از شبکه‌های آینده

شبکه پرداخت نباید به TRON محدود شود.

ساختار باید قابلیت تعریف شبکه‌های جدید را داشته باشد.

شبکه انتخابی کاربر، شبکه واقعی تراکنش و شبکه پشتیبانی‌شده Gateway باید تطبیق داده شوند.

- نتیجه اجرای اکشن‌ها را ارسال کند.
- اطلاعات سلامت نود را گزارش کند.

### 6.2. پیش‌شماره‌ها

تمام پیش‌شماره‌های ثابت موجود در کد باید شناسایی شوند.

هیچ پیش‌شماره‌ای نباید بدون دلیل در کد Hardcode شود.

پیش‌شماره‌ها باید از ساختار دیتابیس و API مربوطه دریافت شوند.

محدوده پیش‌شماره داخلی شبکه:

`1 تا 999`

این پیش‌شماره‌ها شناسه داخلی GetNumber هستند و نباید با کدهای رسمی کشور در E.164 اشتباه گرفته شوند.

هر نود می‌تواند چند پیش‌شماره داشته باشد.

مالکیت هر پیش‌شماره در شبکه باید یکتا باشد.

### 6.3. استقلال Normal Node

در صورت قطع ارتباط با Central:

- پیام‌رسانی داخلی نود همچنان کار کند.
- کاربران محلی بتوانند از امکانات داخلی استفاده کنند.
- عملیات مستقل نود متوقف نشود.
- پیام‌های بین نودی در صف انتظار قرار بگیرند.
- وضعیت قطع ارتباط ثبت شود.

---

# 7. Phase 7: توسعه Central Node

Central Node باید پروژه مستقل باشد.

ابتدا ساختار و معماری مستقل آن طراحی و سپس پیاده‌سازی شود.

### 7.1. ثبت خودکار نودها

مدل ثبت:

Self-Service Auto Registration

هر توسعه‌دهنده بتواند بدون دعوت‌نامه درخواست عضویت ثبت کند.

فرآیند:

1. توسعه‌دهنده اطلاعات اولیه نود را ارسال می‌کند.
2. Central درخواست را دریافت می‌کند.
3. یک Global Node ID یکتا صادر می‌شود.
4. اطلاعات کلید عمومی نود ثبت می‌شود.
5. نود پیش‌شماره‌های آزاد را درخواست می‌کند.
6. Central پیش‌شماره‌های مجاز را پیشنهاد می‌دهد.
7. توسعه‌دهنده یکی را انتخاب می‌کند.
8. پیش‌شماره رزرو می‌شود.
9. ثبت نود تکمیل می‌شود.
10. API Key و مجوزهای مربوط صادر می‌شوند.

ثبت اولیه باید خودکار باشد.

با این حال، سیاست‌های امنیتی، محدودیت‌ها و امکان تعلیق نود باید در اختیار Central باقی بماند.

### 7.2. Global Node ID

هر نود باید یک شناسه جهانی یکتا داشته باشد.

این شناسه نباید با تغییر IP، دامنه یا سرور تغییر کند.

### 7.3. امنیت نودها

هر نود باید قابلیت استفاده از چند API Key مستقل داشته باشد.

هر کلید:

- شناسه مستقل
- سطح دسترسی مستقل
- تاریخ ایجاد
- تاریخ انقضا در صورت نیاز
- قابلیت Rotation
- قابلیت Revocation
- گزارش استفاده

داشته باشد.

برای احراز هویت قوی‌تر از امضای دیجیتال مبتنی بر کلید عمومی و خصوصی استفاده شود.

کلید خصوصی نباید به Central ارسال شود.

درخواست‌های حساس باید دارای Timestamp، Nonce و شناسه یکتا باشند تا Replay Attack جلوگیری شود.

### 7.4. مدیریت پیش‌شماره‌ها

Central مرجع نهایی مالکیت پیش‌شماره‌ها است.

قواعد:

- محدوده 1 تا 999
- پیشنهاد خودکار پیش‌شماره‌های آزاد
- انتخاب توسط توسعه‌دهنده
- امکان چند پیش‌شماره برای یک نود
- عدم تخصیص هم‌زمان پیش‌شماره به دو نود
- امکان سلب مالکیت
- امکان تغییر پیش‌شماره
- امکان تعلیق
- امکان آزادسازی
- ثبت تاریخچه کامل مالکیت

رزرو فقط برای پیش‌شماره انتخاب‌شده انجام شود، نه تمام گزینه‌های پیشنهادی.

### 7.5. رزرو زمان‌دار پیش‌شماره

هر رزرو باید دارای Expiration باشد.

فیلدهای پیشنهادی:

- prefix
- node_id
- status
- reserved_at
- expires_at
- assigned_at

زمان رزرو باید از تنظیمات Central قابل تغییر باشد.

مقدار اولیه پیشنهادی: ۱۵ دقیقه.

Cron Job باید رزروهای منقضی‌شده را آزاد کند.

رزروهای تخصیص‌یافته نباید با Cron Job آزاد شوند.

عملیات رزرو و تخصیص باید اتمیک باشد.

# 8. مدیریت پوشش شبکه و API پیش‌شماره‌ها

Central باید مرجع اطلاعات پوشش شبکه باشد.

نام نمایشی هر پیش‌شماره باید از مقدار عددی آن مستقل باشد.

امکان مدیریت موارد زیر وجود داشته باشد:

- Prefix
- نام نمایشی
- نام فارسی
- نام انگلیسی
- وضعیت
- مالک
- توضیحات
- تاریخ تخصیص
- تاریخ تغییر مالکیت

این نام‌ها نشان‌دهنده پوشش و دسته‌بندی داخلی GetNumber هستند و الزاماً نام کشورهای واقعی نیستند.

### API عمومی پوشش شبکه

Endpoint پیشنهادی:

`GET /api/v1/coverage`

خروجی باید شامل:

- فهرست پیش‌شماره‌های فعال
- نام نمایشی هر پیش‌شماره
- وضعیت پوشش
- اطلاعات موردنیاز برای نمایش در Normal Node

باشد.

همچنین APIهای زیر طراحی شوند:

- دریافت اطلاعات یک پیش‌شماره
- دریافت فهرست براساس وضعیت
- دریافت نسخه فعلی Coverage
- دریافت تغییرات جدید
- دریافت فهرست کامل پیش‌شماره‌های فعال

نودها باید بتوانند اطلاعات پوشش را Cache کنند و در صورت تغییر، آن را بروزرسانی کنند.

# 9. Phase 8: Node Action Management

این زیرسیستم از اجزای اصلی Central Node خواهد بود.

هدف آن این است که Central برای اجرای عملیات به IP یا دامنه ثابت نودها نیاز نداشته باشد.

## 9.1. معماری ارتباط

مدل ارتباط:

Pull-Based Architecture

هر نود خودش به Central متصل می‌شود.

Central فرمان‌ها را در صف پایدار نگه می‌دارد.

نودها در بازه‌های مشخص فرمان‌های جدید را دریافت می‌کنند.

بنابراین حتی اگر IP یا دامنه نود تغییر کند، ارتباط مدیریتی برقرار می‌ماند.

## 9.2. Node Agent

هر Normal Node باید دارای یک Node Agent باشد.

این Agent مسئول موارد زیر است:

- ارتباط خروجی HTTPS با Central
- دریافت اکشن‌ها
- بررسی اعتبار اکشن
- بررسی امضای دیجیتال
- بررسی مجوزها
- جلوگیری از اجرای تکراری
- اجرای عملیات مجاز
- ارسال نتیجه
- ارسال Progress
- گزارش خطا
- تلاش مجدد پس از قطع ارتباط

پروتکل Node Agent باید مستقل از Laravel باشد.

توسعه‌دهندگان دیگر باید بتوانند آن را با زبان‌های برنامه‌نویسی متفاوت پیاده‌سازی کنند.

## 9.3. مدیریت اکشن‌ها در Central

برای هر نود یک صفحه مدیریت اکشن وجود داشته باشد.

ادمین بتواند:

- اکشن جدید ثبت کند.
- اکشن را لغو کند.
- وضعیت اکشن را ببیند.
- نتیجه اجرا را مشاهده کند.
- خطاها را مشاهده کند.
- اکشن ناموفق را مجدداً اجرا کند.
- تاریخچه اکشن‌ها را بررسی کند.
- اکشن را برای چند نود ثبت کند.

## 9.4. انواع اکشن

انواع اولیه:

- SYNC_PREFIXES
- MIGRATE_PREFIX
- SYNC_ROUTES
- ROTATE_API_KEY
- REFRESH_CONFIG
- HEALTH_CHECK
- DISABLE_ROUTING
- ENABLE_ROUTING

اکشن‌ها باید از نوع‌های از پیش تعریف‌شده باشند.

اجرای دستور Shell دلخواه یا اجرای کد ناشناس روی نودها ممنوع است.

## 9.5. مدیریت Expiration و آفلاین بودن نودها

این بخش بسیار مهم است.

نباید فرض کنیم تمام نودها همیشه آنلاین هستند.

ممکن است نودی برای چند ساعت یا چند روز آفلاین باشد.

معماری صف باید Durable باشد.

فرمان‌های مهم نباید با قطع ارتباط نود حذف شوند.

دو مفهوم باید کاملاً جدا باشند:

### A. Delivery Lease

مدت زمانی که یک نود برای دریافت یا تکمیل یک تلاش اجرایی فرصت دارد.

اگر نود اکشن را دریافت کرد ولی نتیجه‌ای نداد یا در زمان اجرا از دسترس خارج شد:

- Lease منقضی شود.
- اکشن دوباره قابل دریافت شود.
- اجرای دوباره با همان Action ID انجام شود.
- از اجرای اثر تکراری جلوگیری شود.

### B. Business Expiration

زمانی که یک اکشن از نظر تجاری دیگر معتبر نیست.

این زمان باید براساس نوع اکشن تعیین شود.

قواعد:

1. اکشن‌های حیاتی مانند MIGRATE_PREFIX نباید صرفاً به‌دلیل آفلاین بودن نود حذف شوند.
2. اکشن‌های حیاتی می‌توانند تا دریافت و اجرای موفق یا لغو صریح توسط Central در صف باقی بمانند.
3. اکشن‌های موقت مانند برخی درخواست‌های Health Check می‌توانند Expiration کوتاه داشته باشند.
4. اکشن‌های منسوخ‌شده باید با اکشن جدید جایگزین شوند، نه اینکه بدون ثبت سابقه حذف شوند.
5. هر اکشن باید سیاست Retry مشخص داشته باشد.
6. Retry باید دارای Backoff باشد.
7. تعداد Retry و فاصله آن‌ها قابل تنظیم باشد.
8. در صورت شکست مکرر، اکشن وارد وضعیت FAILED یا NEEDS_ATTENTION شود.
9. فرمان‌های لغوشده نباید دوباره اجرا شوند.
10. هیچ فرمان منقضی‌شده‌ای نباید بدون بررسی اعتبار زمانی اجرا شود.

### وضعیت‌های اکشن

- PENDING
- DELIVERED
- ACKNOWLEDGED
- RUNNING
- RETRYING
- COMPLETED
- FAILED
- EXPIRED
- CANCELLED
- SUPERSEDED
- NEEDS_ATTENTION

دریافت اکشن با اجرای اکشن متفاوت است.

ACK دریافت به معنی موفقیت عملیات نیست.

## 9.6. جلوگیری از اجرای تکراری

حداقل یک‌بار تحویل (At-Least-Once Delivery) را مبنا قرار بده.

Exactly-Once را بدون اثبات فنی ادعا نکن.

هر اکشن باید دارای:

- Action ID
- Node ID
- Idempotency Key
- Created At
- Issued At
- Expires At در صورت نیاز
- Attempt Count
- Payload
- Signature

باشد.

Node Agent باید قبل از اجرای اکشن بررسی کند که آیا همان Action ID قبلاً اجرا شده است یا خیر.

نتایج عملیات باید در دیتابیس محلی نود نیز ثبت شوند تا در صورت Restart، وضعیت قابل بازیابی باشد.

## 9.7. گزارش اجرای اکشن

هر نود باید نتیجه اجرای اکشن را به Central گزارش دهد.

ساختار نتیجه:

- Action ID
- Node ID
- Status
- Progress
- Started At
- Completed At
- Processed Items
- Failed Items
- Error Code
- Error Message
- Result Data

Central باید بتواند پیشرفت عملیات را به‌صورت زنده نمایش دهد.

---

# 10. Phase 9: تغییر پیش‌شماره و Background Migration

تغییر پیش‌شماره یک نود باید از طریق Node Action Management انجام شود.

مثال:

Node #22

Prefix قبلی: 85

Prefix جدید: 43

### فرآیند

1. Central درخواست تغییر را ثبت می‌کند.
2. پیش‌شماره جدید رزرو یا تخصیص موقت داده می‌شود.
3. اکشن MIGRATE_PREFIX ساخته می‌شود.
4. نود اکشن را دریافت می‌کند.
5. نود دریافت اکشن را ACK می‌کند.
6. Migration در Background شروع می‌شود.
7. شماره‌ها به‌صورت Batch تغییر می‌کنند.
8. Progress گزارش می‌شود.
9. نتیجه به Central ارسال می‌شود.
10. Central مسیرهای جدید را برای نودهای مرتبط ارسال می‌کند.
11. نودهای مرتبط تغییر مسیر را دریافت می‌کنند.
12. تأییدیه دریافت و اعمال ثبت می‌شود.
13. صحت مهاجرت بررسی می‌شود.
14. پس از تأیید شرایط، پیش‌شماره قدیمی آزاد می‌شود.

### قواعد Migration

- Number ID نباید تغییر کند.
- تاریخچه پیام‌ها نباید حذف شود.
- تاریخچه تراکنش‌ها نباید تغییر مخرب کند.
- روابط کاربران حفظ شوند.
- شماره‌ها باید به‌صورت Batch منتقل شوند.
- عملیات باید قابل Retry باشد.
- اجرای مجدد نباید داده تکراری ایجاد کند.
- در صورت شکست، وضعیت عملیات قابل بازیابی باشد.
- تمام مراحل Audit Log داشته باشند.

### مدیریت نودهای آفلاین

اگر یکی از نودهای مرتبط آفلاین باشد:

- فرمان در صف پایدار باقی بماند.
- Central وضعیت انتظار را نمایش دهد.
- پس از اتصال مجدد، فرمان دریافت شود.
- تا تکمیل شرایط ایمنی، پیش‌شماره قدیمی آزاد نشود.

آزادسازی اجباری پیش‌شماره در شرایط اضطراری فقط با عملیات مدیریتی صریح، ثبت دلیل، هشدار امنیتی و ثبت Audit Log مجاز است.

در این وضعیت باید امکان مسدودسازی مسیر قدیمی و قرار دادن پیش‌شماره در دوره قرنطینه وجود داشته باشد.

---

# 11. Phase 10: مسیریابی پیام بین نودها

معماری انتخابی:

Hybrid Routing

ارتباط مستقیم بین نودها در صورت امکان و مجاز بودن برقرار می‌شود.

در صورت عدم امکان یا الزام سیاست‌های مرکزی، پیام از Central عبور می‌کند.

مثال:

Node #22 قصد ارسال پیام به Node #43 دارد.

مراحل:

1. تشخیص مقصد
2. شناسایی مالک پیش‌شماره
3. بررسی اعتبار نود مبدأ
4. بررسی مالکیت شماره مبدأ
5. بررسی مجوز ارسال
6. بررسی مجوز دریافت
7. تعیین مسیر ارتباط
8. بررسی محدودیت‌ها
9. ارسال پیام
10. دریافت ACK
11. ثبت وضعیت تحویل

### کنترل‌های امنیتی

- جلوگیری از جعل شماره مبدأ
- جلوگیری از Replay Attack
- جلوگیری از ارسال تکراری
- محدودیت نرخ درخواست
- احراز هویت نود مبدأ
- اعتبارسنجی نود مقصد
- ثبت گزارش ارتباط
- مدیریت صف در زمان آفلاین بودن مقصد

اگر مقصد آفلاین باشد، پیام باید براساس سیاست نگهداری و انقضای پیام در صف قرار بگیرد.

مدت نگهداری پیام با مدت اعتبار فرمان‌های مدیریتی متفاوت است.

ارتباط داخلی هر نود هنگام قطع Central باید فعال باقی بماند.

- اعتبارسنجی امضای درخواست‌های بین نودی

# 14. الزامات دیتابیس

قبل از طراحی جدول جدید، ساختار دیتابیس موجود بررسی شود.

از ایجاد جداول تکراری و ساختارهای موازی غیرضروری جلوگیری کن.

در طراحی:

- Foreign Key مناسب
- Unique Constraint
- Index مناسب
- Transaction
- Lock
- Soft Delete در محل مناسب
- Audit History

رعایت شوند.

برای عملیات مالی و تخصیص پیش‌شماره، Unique Constraint باید در سطح دیتابیس نیز وجود داشته باشد.

منطق جلوگیری از تکرار نباید صرفاً در لایه Application باشد.
